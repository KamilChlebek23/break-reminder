# Lessons Learned

> Append-only register of recurring rules and patterns. Re-read at start by /10x-frame, /10x-research, /10x-plan, /10x-plan-review, /10x-implement, /10x-impl-review.

## Document every public Python function with a Google-style docstring

- **Context**: Every public function and method in `.py` files across `break_reminder/`, `tests/`, and `main.py`. Private helpers (leading `_`) are exempt unless they encode non-obvious behavior.
- **Problem**: Documentation is inconsistent between files.
- **Rule**: Always attach a Google-style docstring (one-line summary, then `Args:` / `Returns:` / `Raises:` sections as needed) to every public function and method in `.py` files. Enforce via ruff's `D` rule group with `[tool.ruff.lint.pydocstyle] convention = "google"` so violations fail CI rather than relying on review discipline.
- **Applies to**: implement, impl-review

## Bundle /10x orchestration edits into the change's first phase commit

- **Context**: Changes opened via `/10x-test-plan` + `/10x-new` produce orchestration edits (e.g. `context/foundation/test-plan.md` §3 row status: `not started` → `change opened`) BEFORE the first implementation phase starts. The first phase's commit ritual finds these as dirty-but-untouched paths.
- **Problem**: The dirty-path prompt at commit time forces a per-commit decision (bundle / defer / abort). Deferring orphans the orchestration edit as a stray modification across multiple phase commits; bundling is the natural fit but isn't documented as the default. `/10x-impl-review` will flag the orphan as "out of phase scope" if reviewed mid-flight (see `testing-storage-malformed-input` Phase 1 F6).
- **Rule**: When the first phase commit ritual surfaces a dirty path that came from `/10x-test-plan`, `/10x-new`, or `/10x-shape` orchestration (typically `test-plan.md` §3 status flips, change-folder cell fills, or shape-notes deltas), default to **bundling** into the first phase's commit. Subject line stays scoped to the phase; body should call out the orchestration edit in one line so a reviewer doesn't have to spelunk. Treat any other dirty path as a genuine "unrelated" prompt.
- **Applies to**: implement, impl-review

## Storage-boundary loaders need per-row containment + per-field coercion

- **Context**: Every `from_dict` / `_get_*` / `load()` boundary in `break_reminder/storage/` (today: `reminders.py::Reminder.from_dict` + `ReminderStore._read`; `settings.py::Settings._get_int` / `_get_bool` / `_get_str`). FR-002 / FR-011 / FR-015 designate these files as user-editable in Notepad, so every disk read must treat its input as potentially hostile — a hand-edit, a partial-write crash, or a forward-compat key from a newer build.
- **Problem**: Two distinct failure classes need distinct fixes, and missing either one is silently dangerous. **Field-level**: a hand-edited single field (`lead_minutes = "oops"`, `start_at` dropped its tz suffix) crashes downstream code without per-field protection. **Row-level**: one malformed row in a multi-row list crashes the entire load when the per-row parse call sits outside any try/except, vaporizing well-formed siblings. The S-06b retrospective (impl-review F4 at `context/archive/2026-05-27-reminders-lead-time/reviews/impl-review-phase-1.md:84-92`) surfaced the field-level lesson via `_coerce_lead_minutes`, but it was never generalized to the row-level pattern until `testing-storage-malformed-input` Phase 3 closed `ReminderStore._read`. Both layers are required.
- **Rule**: At every storage-layer disk-read boundary, **both** layers must be present. **(a) Field-level**: every hand-editable field has a `_coerce_*` helper that maps any input (wrong type, out-of-range, malformed) to either a safe value or a documented exception class. Canonical example: `_coerce_lead_minutes` at `break_reminder/storage/reminders.py:51-83` (range clamp + type fallback). **(b) Row-level**: the boundary-level loader wraps per-row parse calls in `try/except` against the documented exception tuple (e.g. `(KeyError, ValueError, TypeError)` for `Reminder.from_dict`), drops the bad row with a `logger.warning` naming the row index + exception class, and preserves well-formed siblings. Canonical example: `ReminderStore._read` post-Phase-3 at `break_reminder/storage/reminders.py` (per-row guard + `isinstance(raw, list)` top-level guard that collapses non-list JSON to a single "top-level is not a list" WARNING). When introducing a new persisted field or a new storage boundary, ask both questions explicitly: "does the field have a `_coerce_*` helper?" AND "does the loader's exception tuple include every class this field can raise?" Mirror this audit in any `/10x-plan` that touches storage.
- **Applies to**: plan, implement, impl-review

## Signal-connection assertions are not end-to-end coverage

- **Context**: Any cross-module Qt signal connection in `break_reminder/app.py` (today: `:287` `break_due → _on_break_due`, `:288` `reminder_due → _on_reminder_due`, `:359` `break_interval_changed → _on_break_interval_changed`) or analogous wiring sites in future modules (`QAction.triggered.connect`, `dialog.signal.connect`, scheduler signals into app slots). Whenever a test asserts a connection exists OR captures the connected slot and invokes it by hand, the test fails to exercise the production signal-emit path.
- **Problem**: Tests that pass while the actual connect line is broken. Four canonical `_StubSignal` shims in this codebase (`tests/test_app.py:431`, `tests/test_settings_dialog.py:2446` / `:2749` / `:2802`) capture the slots connected to a dialog's signal and then drive them via `slots[0](value)` in the test body. The shim pattern lets the test pass even if (a) the production code never connects the signal in the first place, (b) the connect target was changed to the wrong slot, or (c) the signal-emit ordering inside `accept()` regressed. The canonical example is `tests/test_app.py:285-314` (`test_end_to_end_via_settings_dialog_stub`) — named "end-to-end" but exercising none of the cross-module wiring. The four Phase 4 e2e files (`tests/test_*_e2e.py`) deprecate this pattern by emitting real signals across real `.connect()` calls into real production slot bodies, with the load-bearing assertion oracled on the user-visible outcome (dialog on `QApplication.topLevelWidgets()`, CSV row appended via `(event_type, outcome)` tuple, persisted INI key value). Mutation tests during Phase 4 implementation confirmed each connect line genuinely breaks its e2e test when commented out.
- **Rule**: Cross-module wiring contracts require an end-to-end test that **emits the real signal across the real `connect`** and observes the **real downstream slot's user-visible effect** (dialog appearance on `QApplication.topLevelWidgets()`, CSV row content, INI key value, persisted file content). Slot capture-and-invoke (`captures[0]["slots"][0](value)`, `_StubSignal` shims that record `connect` calls without ever emitting, `Mock()` of the slot with `.assert_called_with(...)`) is acceptable for unit-testing the slot body in isolation but does NOT count as wiring coverage — it cannot catch a regression of the `.connect()` call itself. When the production wire happens on-demand inside a method that blocks the test thread (e.g. `_on_open_settings` calls `dialog.exec()` at `app.py:360`, so the `break_interval_changed.connect(...)` at `app.py:359` is unreachable from a non-blocking test), use the hybrid pattern documented in `tests/test_save_settings_interval_e2e.py`: mirror the on-demand connect locally in the test (byte-for-byte same target slot) and document the residual gap in the test docstring. Canonical examples: the three Phase 4 e2e files (`tests/test_add_reminder_e2e.py`, `tests/test_save_settings_interval_e2e.py`, `tests/test_tray_reset_e2e.py`) plus the cookbook recipe at `context/foundation/test-plan.md §6` "Cross-cutting end-to-end flows". When the test deliberately relies on a precondition that mirrors implementation state (e.g. `_active_seconds == 0`, `_timer.isActive()`) to surface a regression with a clear diagnostic before the load-bearing oracle, the precondition is acceptable — but it must NEVER be the only assertion, and the docstring must explicitly call it out as a precondition (mirrors test-plan §2 R-3 implementation-mirror caveat).
- **Applies to**: plan, implement, impl-review

## RRULE math against a UTC-anchored `dtstart` drifts across DST — always localize to an IANA name first

- **Context**: `dateutil.rrule.rrulestr(rule, dtstart=...)` calls in `break_reminder/scheduler.py::next_firing_after` and any future site that anchors recurring instants to a wall-clock the user typed in a specific timezone. Applies whenever a persisted `start_at` is the anchor of a daily / weekly / monthly RRULE.
- **Problem**: With a UTC-anchored `dtstart` (e.g. `datetime.now(UTC)` or a naive ISO string the storage layer normalized to UTC without remembering the original zone), `rrulestr` walks the UTC calendar. The UTC instant of each firing stays stable but the user's wall-clock interpretation drifts by the DST offset on the first post-transition firing — a "Daily 9:00 Warsaw" reminder set in February starts firing at 10:00 Warsaw on the spring-forward Sunday and keeps that 1-hour drift until the next transition. The failure is invisible to any unit test whose `now` and `dtstart` both sit on the same side of a DST boundary, which is exactly how R-1b shipped undetected through S-08's `reminders-recurrence-editor` and survived four days in production. The S-08 plan even claimed "RRULE handles DST correctly" — a scope error: that claim was only true for the `_local_date_to_utc_end_of_day` end-date conversion, NOT for `next_firing_after` recurrence math.
- **Rule**: Whenever you anchor recurring math to a user-typed wall-clock instant, localize **both** `dtstart` and the comparison `now` to a stored IANA name (`ZoneInfo("Europe/Warsaw")`, NOT a fixed offset like `timezone(timedelta(hours=1))`, NOT `datetime.utcnow()`) **before** calling `rrulestr`. The IANA name belongs on the same persisted object as the `start_at` instant (canonical example: `Reminder.tz` field added by `bugfix-reminder-dst-drift`). Defend the zone-resolution call with `try/except (ZoneInfoNotFoundError, ValueError)` and a UTC fallback so a corrupt or hand-edited tz string never crashes the scheduler — canonical example: `break_reminder/scheduler.py::_resolve_zone`. Storage-layer coercion should mirror the same exception tuple — canonical example: `break_reminder/storage/reminders.py::_coerce_tz`. When writing tests for recurring firings, pick a `now` value that **traverses** a DST boundary between `start_at` and the firing under test (e.g. `start_at` on 2026-02-01, `now` on 2026-03-28 08:30 UTC for an `Europe/Warsaw` reminder); a `now` value on the same side of the boundary as `start_at` cannot detect the bug. Cross-references: `context/archive/2026-06-02-bugfix-reminder-dst-drift/` (the bugfix + research + plan + impl-review); `AGENTS.md` "FR-014 — recurrence engine" section (corrected to qualify the "RRULE handles DST" claim with "when `dtstart` carries an IANA-named timezone").
- **Applies to**: plan, plan-review, implement, impl-review

## PyInstaller data-only packages (`tzdata`, similar) need `--collect-data`, not `--collect-submodules`

- **Context**: Any new runtime dependency that is a **data-only** package — i.e. ships `.zoneinfo` / `.json` / `.dat` / etc. files rather than Python modules. Today: `tzdata` (IANA zone database, required by stdlib `zoneinfo` on Windows). Future analogs: `certifi`'s root-CA bundle if ever bundled standalone, `babel`'s locale data, etc. Distinct from `pynput`-style dynamic-import packages whose drift is mitigated by `--collect-submodules`.
- **Problem**: PyInstaller's static analyzer discovers code by walking `import` statements but does NOT bundle non-Python data files unless explicitly told to. Without `--collect-data tzdata`, the packaged `.exe` silently ships without any `.zoneinfo` files, and the first `ZoneInfo("Europe/Warsaw")` call at runtime raises `ZoneInfoNotFoundError` — but only in the packaged binary, never in local dev or CI tests, because `uv sync` installs `tzdata` directly into the venv where stdlib `zoneinfo` finds it. The failure mode is invisible to every gate except a real install on a real machine, which is exactly how an unsigned-binary first-run path tends to surface bugs late.
- **Rule**: When adding a runtime dep to `pyproject.toml`, ask: "does this package ship Python modules, data files, or both?" If it ships data files (or both), add the corresponding `--collect-data <pkg>` flag to the PyInstaller invocation in `.github/workflows/release.yml` AND mirror it in the local-build snippet in `README.md` "Build a Windows installer locally" AND in the inline comment at `pyproject.toml`'s PyInstaller section. Canonical example: `tzdata` requires `--collect-data tzdata` per `bugfix-reminder-dst-drift`. A regression check is straightforward — run the packaged `.exe` once on a clean Windows VM (no Python venv on PATH) before tagging, OR extend `main.py --self-test` to exercise the data path (e.g. `ZoneInfo("UTC")` for `tzdata`) and rely on the release workflow's existing `--self-test` step. Cross-references: `context/archive/2026-06-02-bugfix-reminder-dst-drift/` (where the gap was identified); `context/foundation/infrastructure.md` risk register (`pynput` dynamic-import drift row is the dynamic-import analog of this data-file rule).
- **Applies to**: plan, implement, impl-review
