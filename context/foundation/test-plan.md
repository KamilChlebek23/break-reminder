# BreakReminder — Test Plan

> Phased rollout strategy that turns BreakReminder's zero-integration-test gap into a four-phase test program. The `## Phased rollout` table in §3 is the orchestrator's state machine — re-run `/10x-test-plan` and it reads §3 to figure out where the rollout is and what to hand off next. Sections §1, §2, §4, §5, §7 are frozen until `/10x-test-plan --refresh`; §3 status cells and §6 cookbook patterns evolve as phases land.

## §1. Strategy

Three principles every phase obeys. They are the load-bearing rules that make the rollout coherent.

1. **Cost × signal.** Every test added — classic or AI-native — must answer one question: *what is the cheapest test that gives a real signal for this risk?* Do not promote to e2e because it "feels safer"; do not stack a heavier framework on top of a deterministic check that already catches the regression. Cheapest does not mean fastest — it means lowest cost (authoring + maintenance + flake) for the same signal. This rule is inherited by every downstream `/10x-plan`.
2. **User concerns are evidence.** Lived incidents in the Phase 2 interview (see §2 Source column entries `Q1`–`Q5`) carry the same weight as PRD lines and hot-spot directories. A risk that is double-cited from the interview AND visible in the git hot-spot scan is the highest-conviction target.
3. **Risks are scenarios, not code locations.** §2 risk rows describe **observable failure scenarios** ("recurring reminder fires once and goes silent next week", "popup is on screen but unclickable while Settings is open"). They **never** name a file:line, function, schema, or module as the failure anchor. That anchor work is `/10x-research`'s output, produced per rollout phase against the up-to-date code. Hot-spot directories cited in the Source column are *likelihood evidence*, not anchors — they explain why a risk is more likely, not where it lives.

## §7. Negative space

Test surfaces this rollout explicitly **will not** invest in. Lifted from the Phase 2 Q5 answer plus PRD § Non-Goals. If a future change appears to demand any of these, it must be re-justified via `/10x-test-plan --refresh`, not by silently bending the rollout.

- **No multi-platform CI.** Windows 11 only (PRD § Non-Goals lines 169). No `macos-latest`, no `ubuntu-latest`, no Windows 10 matrix entry. CI stays `windows-latest`.
- **No deep Qt-internals mocking.** Do not mock `QTimer.singleShot`, `QDialog.exec`, `QStandardPaths`, `QSettings` internals, or `QApplication` lifecycle. Use the existing session-scoped `QApplication` fixture, real `QSettings(IniFormat)` against `tmp_path`, and virtual-clock injection (already a codebase pattern). Mocking Qt internals only proves Qt works the way the test author thought it works, which is not a useful signal.
- **No pixel-perfect tray-icon visuals.** The clock-hand graphic is rendered via `QPainter`; `windows-latest` is headless enough that visual snapshots break constantly without catching real regressions.
- **No NSIS installer UI automation.** Humans drive the NSIS UI; FR-001 acceptance is human-verified per `context/deployment/deploy-plan.md`. Automating clicks through `nsis.exe` in CI is a tarpit.
- **No pinning of `pyttsx3` / Win32 / Qt vendor error strings.** These churn across version bumps; tests that assert on exact wording break without signal.
- **No abuse / authZ / payments / network test surfaces.** The product has no auth, no payments, no outbound network (PRD NFR "Local-only data"). The only abuse-class risk that survives is hand-edited storage tampering, and that is R-5 in §2.
- **No DST-drift fix for recurring firings.** Phase 1 research surfaced that recurring reminders silently drift ±1h across DST transitions because RRULE math runs in UTC space against a UTC-invariant storage layer (see `context/changes/testing-rrule-reminder-loop/research.md` §R-1b). The fix changes the `Reminder.start_at` invariant from UTC to IANA-tz-aware; it warrants its own `/10x-shape` cycle as `bugfix-reminder-dst-drift`. The `TODO(R-1b)` comment block in `tests/test_recurring_reminder_integration.py` carries the breadcrumb. Re-evaluate this entry when the bugfix change opens.

## Refresh cadence

Re-run `/10x-test-plan --refresh` when any of the following are true:

- A new top-3 risk surfaces (post-incident or post-roadmap-pivot) and §2 cannot represent it without `--refresh`.
- A recommended tool / MCP in §4 has its `checked:` date older than 3 months and a stack-sensitive recommendation depends on currency.
- The tech stack changes (e.g., Qt 6 → Qt 7, pytest → pytest 9, dropping pynput for a Win32 hook).
- §7 negative space no longer matches what the maintainer believes (e.g., a contributor adds a second OS and CI grows a Linux matrix).
- All §3 rows are `complete` and the rollout enters maintenance mode — a refresh that asks "what does the new top-N look like?" is the right next step.
